## 3. `最新讨论想法.md`(V1 设计稿) vs 现有代码:delta 审计 + 三件拍板

对 `build_windows_spark.py`/`window_stream.py`/`window_mae.py`/`train_windows.py`/`encode_windows.py`/`level2.py`/`tests/test_windows.py` 逐节比对。**结论:数据层(events→curve)基本对齐,训练层"样本单位"和"特征/掩码语义"有 3 处硬冲突。**

### 必须改(结构性)

- **P0-1 聚合粒度**:文档 §10/§16 定义 Sample=(modeling unit, anchor),unit ≤200m。代码 `sub_id=floor(position/sub_length_m)`(build:159)已算出 unit,curve 也按 (snapshot,pass,sub) 分组(build:165)✓,但 `GROUP` 不含 sub_id(build:16)、`snapshot_id` 是 link 级(build:157)、`_pack` 按 snapshot_id 攒行(stream:38-74)、`window_mae.py:83` 一条 1455m link 只出一个 CLS。**后果:导出的整 link 向量无法与 `eta_data.py` 的 200m 子路段单元 join**。改:GROUP 加 sub_id、snapshots 补 unit_start_m/unit_length_m、curves 补 unit_length_m、encode schema 加 sub_id;**pass cap 保持 link 级**(否则同一辆车穿 8 个 unit 重复计数)。
- **P0-2 第二层只喂可见 trajectory**:文档 §14 图写死 `[CLS]+r_A+r_C+r_E`,被 mask 的不进第二层;代码 stream:83 把所有 curve 都喂进去,被 mask 的 curve 因 `geo` 从不被 mask(window_mae.py:63)退化成"只带几何的 token"。`level2.py:75` 无 MASK token 参数,要加。
- **P0-3 mask 粒度**:文档 §14/§16 反复强调 mask 对象是 Trajectory Token 不是 Bin Token;代码是 bin 级 span mask(无条件生效)+ whole-pass mask(p=0.5)并存(window_mae.py:17-34)。K=1 snapshot 无可 mask 目标(代码已有 `len(passes)>1` 守卫),建议 span mask 降为 K=1 fallback。

### 必须改(参数/特征)

- **P1-1** window/stride 默认 600/60 → 文档 §8 主设置 **600/600**(submit_windows_yarn.sh:13、build:34-35);5/5、20/20 为 ablation。
- **P1-2** bin 特征:文档 §11 是 `[Δt, ratio, observed] + s_i/L_unit`;代码是 `[log1p(Δt/distance), distance/10, position/1000, position/link_length, age, observed, mask]`(window_mae.py:60-77)。缺口:raw Δt 没有、`pos_rel` 分母是物理 link 而非 L_unit、`age`/`pos_abs` 是文档没有的额外特征(§12 只允许作独立 ablation)。
- **P1-3** `max_bins=40` 与 200m 上限不自洽(40 bins=400m 才拒),应收 `ceil(200/10)+1=21`;reader padding 宽度随之从 40 降到 21。

### 三件拍板(本会话结论)

1. **decoder 保留 CLS 瓶颈**。文档 §14 画的 `Hidden States → Decoder` 正是记忆里 V2 警告的 skip connection(V1 双稳态/分支死亡的成因)。decoder 输入改为 `[geo_query, r_unit, MASK_token]`,**摘掉 `z`(level-1 曲线 CLS)**——`z` 来自该曲线自己的可见 bin,对 span-masked bin 就是局部插值捷径。文档版本做成 `--decoder-input cls|hidden` 开关,用分支死亡监控(eval 置零 CLS 看重建误差涨幅)判优劣。
2. **重建目标口径统一为 `Δt_eff = Δt × 10 / distance`**(等效 10m 时长)。distance=10 时严格退化为文档 §3.1 的 Δt;partial bin(distance<10)时可比。是否再套 log1p 作为 `--target-transform raw|log1p` 单独 ablation(现状是 log1p)。
3. **跨 unit 边界的 bin 维持"按起点归属、不裁切"**(管线 §1 既定)。理由:文档 §4.1/§5 明确反对匀速裁切(ratio 是空间归属、observed 是 fix 指示,都不含时间比例)。配套口径:`L_unit = min(sub_length_m, L_link − sub_id×sub_length_m)`(标称长度,文档 §12 的 80m→bin7=0.875 就是这个分母),`pos_rel = (position_m − sub_id×sub_length_m) / L_unit`。

**净产出**:①完整 delta 清单(4 类,含 file:line);②三件拍板结论与落地口径;③未改码。下一步按用户节奏逐点推进,P0-1 优先(其余改动的地基)。

## 7. P0-3 落地:mask 粒度改成整条 trajectory

**依据**:§14「MAE 的 mask 对象不是 bin,而是整条 trajectory」+ §16「Multi-Trajectory MAE mask 的是 Trajectory Token,而不是 Bin Token」。

**新语义**(`window_mae.reconstruction_mask`)

- 多轨迹 snapshot(K≥2):每条轨迹以 `whole_pass_probability` 独立隐藏,再**夹紧**到「至少隐藏 1 条、至少保留 1 条可见」。
- 单轨迹 snapshot(K=1):退化为曲线内连续片段 mask(`mask_ratio`),因为没有任何其他轨迹可以拿来重建它。
- `whole_pass_probability=0`:关闭整条轨迹路径,所有 snapshot 走片段 mask(span-only 消融)。
- padding/无效 bin 永不被 mask(返回值统一 `& valid`)。

**为什么夹紧「至少隐藏 1 条」**:纯 Bernoulli 下 K=2、p=0.5 有 25% 的 snapshot 一条都没被隐藏,`reconstruction_loss` 按「有遮挡的 snapshot 才计损失」的口径会把它们整体丢掉——稀疏路段(K=2~3)浪费明显。补一个「空选则随机补一条」后,这批数据 `train_supervised_snapshots` 从 6/8 回到 8/8。该夹紧在 p=0.5 下对边际隐藏概率无偏(K=3 手算:(1/8+3/8)×(1/3)+(3/8+1/8)×(2/3)=1/2)。

**改动**:`window_mae.py` 重写 `reconstruction_mask`;`train_windows.py` 两个 mask 参数 help;`configs/pretrain_windows.yaml` 注释;`md/窗口管线使用.md` §5;`tests/test_windows.py` 把 `model_batch()` 里的闭包 `item()` 提成 `model_item(sid, n_curves=3)`(K=1 需要单曲线样本),新增 `test_whole_trajectory_mask_is_the_main_path`、`test_mask_never_empties_a_snapshot_and_falls_back_for_one_trajectory`。

**本地验证**:`py_compile` 通过;`pytest -k "bin_features or mask_no_target or whole_trajectory or never_empties"` → **4 passed, 8 deselected**;本地 train/encode 复跑 → `train_supervised_snapshots 8/8`、`train_masked_bins 14`、导出 8 条。断言覆盖:masked 只落在 valid 上、多轨迹 snapshot 无「半条轨迹」mask、每个 snapshot 至少 1 可见 + 至少 1 隐藏、K=1 走片段、p=0 时没有任何整条被隐藏。

**依据**:§14 的图——`[CLS] + r_A + r_C + r_E` 进 Multi-Trajectory Transformer,输出 `CLS` 与 `Hidden States`,Hidden States 进 Decoder 重建被 mask 的轨迹;§16 最终表征取 CLS。

**为什么"替换"比"不喂 z"更强**:被整条隐藏的轨迹在第二层是 MASK token,**它的第一层表征被替换掉、根本没进序列**,所以解码器即使想走 skip 也无处可读;可见轨迹仍以 `z` 进序列(它们没有重建目标)。判定 `hidden_curve` 用的是「所有 valid bin 都被 mask 且至少有一个 valid bin」,所以 span mask(部分遮挡)的曲线仍是正常可见 token。

**分支死亡监控的读法**:`val_aggregate_gap = 置零第二层状态后的损失 − 正常损失`。**init 时它很小是正常的**(随机初始化下解码器对状态本来就不敏感);要看的是它随训练是否拉开——若长时间贴着 0,说明解码器绕过了聚合,即 V2 那个 CLS 分支死亡的坑复发。本地 1 epoch/16 维 smoke:`hidden` 模式 gap=0.0311、`cls` 模式 gap=0.0238(基线 loss 均 ≈1.03)。

## 16. build 慢在哪:一次性的结构问题 + 三处可改的重算

用户问「这个方法能优化么,还是做这一次后面就不用做了」。**两层答案。**

### 结构层:build 不必按天重复(最大的一条)

剩下 6 天的计划是 **adapt 每天一个作业(各带前一小时预热)+ build 一个作业读 7 天 events**,一次出整周语料(1008 个 anchor)。所以「40 分钟 count + 三表写入」**整周只付一次**,加上今天这次试跑共两次。优化点不是把单次做快,而是不重复做。今天这份 24h 语料仍然有用(闸门 + 首次训练看效果),整周语料是另一个目录,训练时指向它即可。

### 代码层:同一份 lineage 被算了 N 遍

elapsed 26:40 里 job 0–8 只占约 7 分钟,**job 9 一个人吃掉 20 分钟**。三处:

1. **`curves` 没 persist**(`tools/build_windows_spark.py:214-218`)。第 217 行的 `size(bins) > max_bins` 校验 count 会**完整重算一遍曲线聚合**(members 的 groupBy + collect_list + sort_array,即那 40800 个 task);随后写 `window_curves` 还要再算一遍。加 `curves.persist(DISK_ONLY)` 省掉其中一次全量聚合。
2. **校验 count 跑在未缓存的上游**。第 165 行(`available_ts` 有限性)与第 170 行(版本冲突)的 count,输入是 `df`——由 49 GB parquet 现场读 + 过滤得到、没有缓存,所以每个 count 都把 49 GB 重读再重过滤一遍。改法:先做 dedup、`events.persist()`,**把校验搬到 persist 之后**,或把三个校验合并成一次 agg。
3. 第 276 行 `members.limit(1).count()` 因为 members 已 persist,本来就是便宜的。

### 不能动的三处(契约决定,砍了就改语料语义)

- `explode` 展开:每个 bin 落进它合法的每个 anchor(600 s 窗 / 600 s 步长 → 平均 1–2 个),这是窗口语料的定义。
- 曲线的 `groupBy + sort_array`:曲线内 bin 必须按 `position_m/bin_idx` 有序。
- `repartition(800, "snapshot_id")`:读端 `target_link_v1/data/window_stream.py:3-4,96` 要求「一个 snapshot 不得跨输出文件、文件内按 snapshot_id 有序」;而 groupBy 的复合键哈希 ≠ snapshot_id 单键哈希,所以这次重分区是**必须的**,不是浪费。

## 18. 读端直读 HDFS:可行性实测 + 语料格式文档

选定的方向(AskUserQuestion 选项 C):改写 `target_link_v1/data/window_stream.py` 用 `pyarrow.fs.HadoopFileSystem` 直读 HDFS,彻底去掉 `hdfs dfs -get`。先做可行性实测,再动代码。

**① libhdfs 能起来,但 CLASSPATH 必须手工展开通配符。**
`/usr/local/hadoop-current/lib/native/libhdfs.so` 存在(Hadoop 2.7.2-5556,Java 1.8)。直接 `fs.HadoopFileSystem(host=None)` 报 `AttributeError`,而 `fs.FileSystem.from_uri('hdfs://DClusterNmg3/...')` 报 `HDFS connection failed / NoClassDefFoundError`。原因不是缺 jar:`hdfs classpath` 输出是**通配符形式**(`share/hadoop/common/lib/*`),而**通配符展开是 `java` 启动器干的活,libhdfs 内嵌 JVM 不展开**——所以 JVM 找不到类。手工把每个 `dir/*` 展开成显式 jar 列表后(535 个条目 / 25.9 KB),`from_uri` 立刻成功,列出 800 个 part 文件 0.3 s。

**② 吞吐够用。** 单文件 252,248 行 / 2 row group;`open` 0.25 s、读 8192 行 1.40 s、`read_row_group(0)` 0.98 s;4 线程并发各读 8192 行 wall 2.26 s。按 `MAX_BATCHES=5000 × BATCH_SIZE=8 = 40,000` snapshot 算,一个 epoch 的取数在秒级,不是瓶颈。退出时 pyarrow 报 `FSDataInputStream#close error: Filesystem closed`——解释器关闭顺序问题,无害,但要在代码里显式管。

**③ fork 后 JVM 必死——这是真正的拦路虎。** DataLoader 默认 `num_workers=4` 走 fork,而 `__iter__` 在子进程里跑。实测:子进程**继承**父进程的 fs → 挂死 90 s(超时);子进程**自己重建** fs → **同样挂死**,且日志里出现 `hdfs-site.xml` 的 XML include 拉取失败。根因是 **fork 只复制调用线程,JVM 的内部线程全部丢失**,子进程里任何 JVM 调用都会永久阻塞——所以"每个进程自建 fs"并不能解决 fork 的问题。唯一出路是 **spawn**(fork+exec 全新解释器,各自建 JVM),即 DataLoader 传 `multiprocessing_context="spawn"`,代价是每 worker 一次 JVM 启动 + 重新列文件,且 `WindowDataset` 必须可 pickle(需 `__getstate__` 丢掉 fs 句柄)。

**④ 顺手写了语料格式文档** `md/窗口语料数据格式.txt`:四张产物的粒度、`window_curves` 一行的列定义与实拍样例行、`bins` 每个字段的语义、读端硬断言的因果契约(`bin_start_ts >= anchor-600`、`bin_end_ts < anchor`、`available_ts <= anchor`)、`_pack` 的定长化与 `age` 粗化规则、以及本地残片 `.tmp_window_curves/`(上次中断拉取的残留,停在 staging 阶段没污染正式路径,只有 curves 没 meta,不能单独当语料用)。

## 19. 每链路轨迹数量分布(直读 HDFS,精确 distinct)

需求:每条物理链路上的**轨迹数**(一次穿越 = 一个 `sample_id`)分布。定义必须说清:同一 passage 在 `window_curves` 里会出现多行——覆盖多个 `sub_id` 时多行,且它的 bin 跨越锚点边界时会落进两个锚点窗口,所以**既不是行数,也不是逐窗口计数的求和**(后者按"跨越边界的穿越"比例虚高)。

工具 `tools/stats_windows_links.py`:读 `(map_version, target_link_id, sample_id)` 三列 → 每文件把链路字典映射成全局 int32 id → 全量写进预分配的定宽结构化数组 `(link:int32, sid:V51)` → 一次原地排序 → 相邻比较得精确 distinct。**不做哈希,键是逐字节比较,所以无碰撞风险**。链路身份用 `(map_version, target_link_id)`(build 的 `LINK_GROUP` 前两项,同一 link id 可能存在于两个路网版本)。

规模实测:800 文件 / **2.0049 亿行**;三列压缩后仅 **5.18 GB**(其中 `sample_id` 4.69 GB,`target_link_id` 0.48 GB),所以全量直读完全可行。`sample_id` 长度 **37..51**(不是定长!直方图里 42–45 和 49–50 两大簇),所以键宽用自动预扫测出来(只读 `sample_id` 一列,800 文件 40–52 s),而不是写死常数——宽度不足会撞键,必须硬报错。

**事故:第一次全量跑被 OOM 杀掉**(RSS 24.7 GB,cgroup 上限 30 GB,kernel 日志 `oom-kill:CONSTRAINT_MEMCG`)。根因不是预分配数组(11 GB),而是 **`ThreadPoolExecutor` 的 future 会一直持有结果**:`as_completed` 里 `fut.result()` 取完值,future 对象仍引用那份结果,800 个文件的 `values/codes/sids` 全留在内存里(800 × 16.5 MB ≈ 13 GB),加上数组 11 GB 正好 24 GB。**教训:用 `as_completed` 必须自己丢引用,或者改成有界批次的 `ex.map`**(已改为每批 32 个文件,峰值降到 ~11.5 GB)。

顺带砍掉一处白工:原先每文件做一次 numpy 排序去重(252k 行 0.7 s × 800 = 560 s),但实测文件内重复只有 **0.035%**(file0: 252,248 行 → 252,160 对),收益远小于代价——改成全部追加、只做一次全局排序,重复交给全局排序消掉。per-file distinct 仍用 `pc.count_distinct`(C++ 0.09 s/文件)算出来,用来量化"跨文件重复"占比。

**踩坑记录**:`pc.group_by(...).aggregate([("sample_id","count_distinct")])` 在**单批次 65k 行**上要 31.9 s(2000 行/秒),但在**整文件 252k 行**上只要 0.09 s——第一次的 32 s 是初始化假象,别据此否掉这个算子。

## 20. 新规范(`md/最新讨论想法.md`)落到原始数据上的核对

用户说明之前理解有误,给出新规范:建模单元 = 原始 `seg_idx`(约 500 m),窗口 = 10 min(每小时 6 个),窗口归属由 `t_seg_enter = t_ref + T_cum(segment start)` 决定,特征 `[T_diff, ratio, valid]`,时间嵌入 `Δt_k = t_seg_enter − window_start ∈ [0,600)`,每条轨迹一个 token,M 条轨迹随机整条掩码 → 轨迹级 Transformer → h_CLS → MAE 解码器 / 下游。在改码之前,先把规范里每一句声明拿 `data/raw_hdfs`(4 个 part,18.9M 行)核对了一遍。

**① `seg_idx` 就是「marked span」的分段编号,和 `seg_mark` 严格同源。** `seg_idx ≥ 0 ⟺ seg_mark == 1`,两者都是 **bin 级**标签(同一 bin 的所有片段行取同一个值);`seg_mark`:0 = 目标链路之前、1 = 目标链路本身、2 = 之后。每个 `(pair, seg)` 的 bin 数分布:1..50 递减长尾 + **恰好 50 bins 占 2.97%**,51 bins 占 0.05%,**>51 为 0** → 确认 seg_idx 每 50 个 marked bin 递增一次(≈500 m),长链路的末段是余数。最长 link 6005 m / `seg_idx` 最大 11,自洽。

**② `t_seg_enter` 可算,但 `T_cum` 是「片段结束时刻」,不是起点。** 实测:同一 bin 的两个片段 `T_cum` 差 = 后一个片段的 `T_diff`,`T_cum − T_diff` 才是片段起点(例:bin 0 的 0.2 片段 `T_cum=0.280, T_diff=0.280` → 起点 0)。所以规范里的 `t_ref + T_cum(segment start)` 若取该段首 bin 的 `T_cum`,得到的是**首 bin 结束时刻**;取起点应为 `t_ref + (T_cum − T_diff)`。差一个 10 m bin 的通过时间(该段占用时间 median 12.2 s / p90 44.9 s / p99 132.5 s,所以差几秒,只在窗口边界上才影响归属)。

**③ 段的占用时间与窗口的关系。** 段内 bin 序列的跨度:median 12.2 s,p99 132.5 s,max 1169 s(500 m 走 19 分钟,严重拥堵)。**3.52% 的段的 bin 序列会跑出它被分配到的那个 10 min 窗口**(Δ 起点 + 跨度 ≥ 600)。Δt 分布 median 301.8 s、p1 6.1 s、p99 594 s,基本均匀铺满 [0,600) ✓。多段 pair 只有 12,296 / 554,030(2.2%,因为大多数 link 短于 500 m),其中 **8.35% 的各段落在不同窗口** —— 规范举的 09:09:50 / 09:10:25 / 09:11:03 案例真实存在,只是占比小;规则本身对长链路必须按段算,不能用 link 级 t_enter 一刀切。

**④ `ratio` 只有 10 档 {0.1,…,1.0},`T_diff` 已经是「按 ratio 等比拆分后的片段级值」。** 同一 bin 内 `T_diff / ratio` 恒定(实测 3 例:`0.5/0.5 → 1.091/1.091`,`0.3/0.7 → 1.031/2.406`,比值都是 3.437)。所以规范 §3.3 的「time = 0.7 s」**不需要再乘 ratio**——直接取该行的 `T_diff` 即可;`distance = 10 × ratio` 保留。跨 link 的 bin 占 **8.05%**。

**⑤ 范围选择器有坑:`link_id == target_link_id` 不能当「目标链路范围」。** `seg_mark==1` 的行的距离和闭合到 `L_link_m` 的误差是 **[-5,+4] 整数上的均匀分布**(10 m bin 量化的固有误差,与 L 无关),这是正常的;但 `link_id==target` 会把 **21.9% 的 pair 多算 100 m、2.0% 多算 200 m**——目标的 link_id 在 marked span 结束后还继续出现在 4–10 个 bin(40–100 m)之外(实测两例:span 结束于 bin 23/26,同 id 一直延伸到 bin 34/37)。所以:**跨度用 `seg_idx ≥ 0`(=`seg_mark==1`)选,`bin_link_ids` 只在 marked span 内部做 bin 内的片段归属**(marked span 内还有 2.96% 的行的 `link_id` 不是目标,正是 7m/3m 那种拆分)。

**⑥ 缺失值。** `T_diff` 有 0.60% NaN(marked span 内 0.37%),`T_cum` 0.47%;NaN 与 `observed==0` **不是同一件事**(4.6 万 NaN 行里 3.1 万行 `observed==1`)。`observed==0` 占 52.1%(marked span 内 57.3%),这就是规范里的 `valid` 掩码口径。另外 `ratio` 对每个 `(sample, link, bin)` 求和有 **2.84% 不等于 1**(min 0.1),即 bin 的一部分可以完全不属于任何 link。

**与现 V1 流水线的差异(改码清单)**:① 建模单元 200 m `sub_id` → 原始 `seg_idx`(≈500 m);② 窗口归属 `available_ts` 因果闭包 → `t_seg_enter`;③ 特征 `duration/distance/position/age/observed` → `[T_diff, ratio, valid]`;④ 时间编码 bin 级 `age` → 轨迹级 `Δt_k`;⑤ 不再需要 `spatial_start_m` / `sub_id` / `snapshot_id` 里的 `sub_id` / 512 曲线上限;⑥ 新增:同一 `(link, seg, window)` cell 内 M 条轨迹 + 整条轨迹随机掩码 + 轨迹级 Transformer + MAE 解码器。

## 23. V1 canonical corpus build(Ragged,整周)

**拍板落地**(用户 2026-09-09 晚):存 ragged,不物化 16-slot padding。Canonical corpus 按 trajectory observation 一行,保留 `cell_id / sample_id / Δt / n_pieces` + ragged 数组 `T_diff / ratio_pct / observed / valid`;另出轻量 `training_groups.parquet`(K_min=4、M_max=16 下每组的 sample_ids);padding 到 [B,16,50,F] 放 DataLoader collate。**以后改 M/K_min 只重建 group index,不重刷 corpus。**

### 建前的 piece 级实测(一个 part,28.3M raw 行 / 10.2M marked)

| 事实 | 值 | 对 build 的意义 |
|---|---|---|
| ratio 取值域 | **恰好 10 个 {0.1…1.0},ratio×10 100% 整数** | 存 uint8 `ratio_pct`,省 4× |
| pieces per (link,seg,sample) | mean 12.29 / p50 8 / p90 29 / p99 50 / **max 51** | 10 m bin ≤50,跨 link 的 bin 多出一片 → ragged 长度 ≤51 |
| pass_idx 在同一 (link,seg,sample) 内 | **0% 多值** | 不需要 pass_idx 入 key |
| T_cum 在 (bin_idx,sub_idx) 序下 | **100% 单调** | `min(T_cum−T_diff)` == 首片,与 census 口径一致 |
| t_ref 组内 | 完全一致(spread=0) | 每 sample 一个 t_ref |
| 全 NaN 时序的组 | 0.0344% | 与 census 同样丢弃(无窗口可归属) |
| T_diff NaN / observed==0(piece 级) | 0.42% / 62.0% | valid = ¬isnan(T_diff),observed = raw flag |

### 实现

`tools/build_corpus.py`(三 stage,每个读上一 stage 的 HDFS 产出,raw 只扫一次):
1. **obs**:raw → `observations/`。`groupBy(map_version,target_link_id,seg_idx,sample_id)` 聚合出 `min(T_cum−T_diff)`、`max(t_ref)` 与 `array_sort(collect_list(struct(bin,sub,T_diff,ratio_pct,observed,valid)))`;`cell_id = xxhash64("map_version|link|seg|window")`;`Δt = t_seg_enter − window_start`;按 `(day,bucket=cell_id%128)` 分区、分区内按 `cell_id` 排序(cell 的观测同处一桶,便于 DataLoader 取批)。额外带 `map_version/target_link_id/seg_idx/window` 四列,使 cells/groups 两个 stage 不必回读 raw。
2. **cells**:窄读 corpus → `cells/`(cell_id, 四键, window, K)+ 验收基线(K 精确直方图、pieces/obs 形态、逐日统计)。
3. **groups**:窄读 corpus → 窗口函数 `row_number()/count()` over `partitionBy(cell_id) order by xxhash64(cell_id|sample_id)`(**确定性 shuffle,无 RNG**);`g=ceil(K/16)`,`base=K//g`,`rem=K%g`,前 rem 组各 base+1 → `training_groups/`(group_id, cell_id, group_idx, group_size, K, sample_ids[])。
