# Cell MAE 单机多卡训练改造方案

## 1. 目标与边界

本次先改造当前主线 `tools/train_cells.py` ，目标是在一台多 GPU 机器上使用
PyTorch `DistributedDataParallel` （DDP）训练 Cell MAE。启动方式为 `torchrun`，一张
GPU 对应一个训练进程。

首版只做“单机多卡”，不同时扩展到多机。`tools/train_eta.py` 也不放在首版范围内，
因为 ETA 训练的 GPU-resident 数据路径和 Cell MAE 的 `IterableDataset` 数据路径不同，
两者应分别改造和验收。

多卡改造不改变：

- 模型结构、MAE mask 规则和 loss 定义；
- train/val 的日期划分；
- checkpoint 中的模型参数命名，保证单卡和多卡 checkpoint 可交换加载；
- HDFS 语料的格式。

## 2. 当前单卡实现的限制

`tools/train_cells.py` 目前是一个 Python 进程、一个 CUDA device，且所有进程级行为都默认
只有一份：

1. `CellCorpusDataset` 只在 DataLoader worker 之间分片，不认识 DDP rank。直接启动
   多个进程会让每张卡重复训练同一批 group。
2. 每个进程都会创建输出目录、打印日志、追加 `metrics.jsonl` 和覆盖 `last.pt`，
   会发生竞态。
3. train/val loss、K 分桶统计、样本数和吞吐量都是单进程口径。
4. DDP 要求同一训练 step 的所有 rank 都进入 backward。当某个 rank 的 batch 没有可监督
   group，或不同 rank 的 batch 数不一致时，照搬现有 `if train and has` 会卡死。
5. 直接对 DDP wrapper 保存 `state_dict()` 会增加 `module.` 前缀，破坏已有加载契约。

不建议使用 `nn.DataParallel`。它只有一个主进程，模型复制和 gradient gather 都集中在
主卡，数据 reader 也不会自动正确分片。

## 3. 推荐架构

```text
submit_cell_*_job.sh
        |
        | NPROC_PER_NODE=8
        v
torchrun --standalone --nproc-per-node=8 tools/train_cells.py ...
        |
        +-- rank 0 -> cuda:0 -> corpus shard 0 -> backward --+
        +-- rank 1 -> cuda:1 -> corpus shard 1 -> backward --+-- all-reduce gradients
        ...                                                  |
        +-- rank 7 -> cuda:7 -> corpus shard 7 -> backward --+
        |
        +-- all-reduce epoch metrics
        +-- rank 0 writes metrics.jsonl and last.pt
```

训练进程不负责重复下载数据。HDFS `dfs -get` 仍由外层 shell 在 `torchrun` 之前只执行
一次；全部分片落到共享本地/NFS 目录后，多个 rank 再只读使用。

## 4. 代码改造

### 4.1 `tools/train_cells.py`

增加分布式运行上下文：

- 从 `RANK` / `LOCAL_RANK` / `WORLD_SIZE` 读取 `torchrun` 环境；
- 多卡 CUDA 使用 NCCL，并调用 `torch.cuda.set_device(local_rank)`；
- 模型先移到 `cuda:LOCAL_RANK`，再包装为 `DistributedDataParallel`；
- 单卡直接 `python tools/train_cells.py ...` 时继续走原路径，不要求分布式环境。

训练循环需要调整：

- 每个 rank 在每个 step 都执行 `zero_grad -> backward -> clip -> step`。即使当地 batch
  没有可监督 group，也要用带计算图的 zero loss 参与 backward，不能跳过 collective。
- 首版要求每个 rank 的 step 数严格一致。`--max-batches` 在 DDP 下定义为“每个
  rank 的 step 数”；全局每 epoch group 数约为
  `max_batches * batch_size * world_size`。
- epoch 结束后对 loss 分子、有效 group 数、masked bin 数、K 分桶统计等做
  `all_reduce(SUM)`；耗时做 `all_reduce(MAX)`，全局吞吐量用总 batch 数除以最慢 rank 耗时。
- 过程日志只由 rank 0 打印，并标明它是 rank-0 local moving average；epoch 指标是全局口径。
- 只有 rank 0 创建输出目录、写 JSON 和 checkpoint，其他 rank 在边界使用 barrier 同步。
- checkpoint 保存 DDP 内部原模型（`model.module.state_dict()`），不写入 `module.` 前缀。
- `finally` 中销毁 process group，保证正常退出。

还应在 checkpoint 中增加不影响加载的元数据：

```json
{
  "distributed": {"world_size": 8, "backend": "nccl"},
  "effective_batch_size": 256
}
```

### 4.2 `target_link_v1/data/cell_corpus.py`

`IterableDataset` 不能使用普通 `DistributedSampler`，需要在 dataset 内同时考虑 DDP rank
和 DataLoader worker。

推荐首版分片规则：

1. dataset 构造参数增加 `rank` 和 `world_size`，不在 worker 子进程内读取
   `torch.distributed` 状态；
2. 每个 `(day, bucket)` 先使用相同 seed 生成 group permutation；
3. 先应用 `groups_per_partition`，再按 `idx[rank::world_size]` 分给不同 GPU；
4. rank 内的 DataLoader worker 再对 partition 做 `partition_order[worker_id::num_workers]`。

这个顺序保证同一 group 在一个 epoch 内只被一个 rank 读到，且 MAE mask 仍然只由
`(epoch, group_id)` 决定。

代价是每个 rank 会读取同一 partition 的 parquet，只是取不同 group。首版先优先保证
样本不重复、step 对齐和训练正确性；第二阶段再做按 partition 分配的 I/O 优化，
避免首版同时引入“分区大小不均导致 rank step 数不同”的风险。

对当前 weekend 配方，`groups_per_partition=4096`，如果使用 8 卡，则每个 bucket
每个 rank 正好取 512 groups，可以自然对齐。

### 4.3 `scripts/submit_cell_train_job.sh`

增加环境变量 `NPROC_PER_NODE`，默认为 1：

```bash
if [[ "$NPROC_PER_NODE" -gt 1 ]]; then
  torchrun --standalone --nproc-per-node="$NPROC_PER_NODE" tools/train_cells.py ...
else
  python -u tools/train_cells.py ...
fi
```

提交脚本在训练前校验：

- `NPROC_PER_NODE <= torch.cuda.device_count()`；
- `DEVICE=cuda`；
- DDP 首版的 `MAX_BATCHES` 或可推导的固定每-rank step 数已配置；
- 有效全局 batch size = `BATCH_SIZE * NPROC_PER_NODE`。

weekend 脚本里的 `BATCH_SIZE=32` 是单卡局部 batch。如果直接扩到 8 卡，全局 batch
会从 32 变成 256。首次对齐实验建议先设每卡 `BATCH_SIZE=4`，保持全局 batch=32
和原 learning rate 不变；确认 loss 对齐后，再做大 batch/LR 扩展实验。

## 5. 验证计划

### 5.1 CPU 单元测试

- 构造多个 partition 和 group，验证 rank shard 之间两两不相交；
- 所有 rank shard 的并集等于单卡样本集；
- 同 seed/epoch/rank 可重现，更换 epoch 会更换顺序和 mask；
- `world_size=1, rank=0` 与现有行为完全一致；
- checkpoint key 不含 `module.` 前缀。

### 5.2 本地 CPU DDP smoke

用 Gloo 和 2 个进程跑极小合成语料：

```bash
torchrun --standalone --nproc-per-node=2 tools/train_cells.py \
  --device cpu --data ... --val-data ... --out ... --epochs 1 --max-batches 2
```

验收：无死锁，只有一份 metrics/checkpoint，全局 group 数正确，checkpoint 可被非 DDP
`CellMAE` 严格加载。

### 5.3 GPU 对齐 smoke

先用同一小语料跑：

- 1 卡×batch 32；
- 8 卡×每卡 batch 4。

关闭 dropout，固定 seed 和相同全局样本顺序，比较首个 step 前后的 loss 和参数。允许并行
归约带来的小量浮点差，但不允许样本重复或指标相差一个数量级。

再跑 2 卡和 8 卡真实语料 smoke，记录：

- samples/s 和 batches/s；
- 每卡峰值显存；
- GPU utilization；
- NFS 读带宽和 CPU 利用率；
- 单卡到多卡的 speedup。

如果 GPU utilization 下降且 NFS 读放大明显，再进入第二阶段：partition 只由一个 rank
读取，同时引入确定性的均衡分区和等 step 控制。

## 6. 当前全量数据任务的含义

`submit_cell_weekend_final_job.sh` 明确生成：

- train：20260817–20260822，6 天 × 128 buckets = 768 个分片；
- val/test：20260823，1 天 × 128 buckets = 128 个分片；
- 总计：7 天 × 128 = 896 个 day/bucket 分片。

每个 day/bucket 都会分别执行一次 `observations_v2` 和一次 `training_groups_k3`
下载，因此最多是 1792 次 `hdfs dfs -get`。按现有脚本注释的粗略体量，本地/NFS
需要预留约 100 GB 级别空间，并额外预留 checkpoint 和临时目录空间。

这与多卡没有强绑定关系：

- 做 DDP 功能 smoke：只需要少量 bucket；
- 做 weekend final 全量实验：才需要上述 896 个分片；
- 同一 `DATA` 目录里 marker 完整时，重跑不会重复下载；`FORCE_FETCH=1` 才会强制重拉。

## 7. 实施顺序

1. 增加 dataset rank sharding 和单元测试。
2. 改造 `train_cells.py` 的 DDP 初始化、等 step 训练、指标归约和 rank-0 I/O。
3. 改造 shell 启动器，保留 `NPROC_PER_NODE=1` 的原单卡路径。
4. 跑 CPU 2-process smoke。
5. 跑 GPU 1-card vs 2/8-card 对齐 smoke。
6. 对齐通过后再决定是否增大全局 batch/LR，以及是否优化 NFS 重复读取。
